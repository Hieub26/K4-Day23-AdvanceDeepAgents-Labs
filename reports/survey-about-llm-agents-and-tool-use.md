# LLM Agents and Tool Use: Architectures, Evidence, and Emerging Directions

## TL;DR
- LLM agents are best distinguished from plain answer-generation by their ability to interact with an external environment, use feedback, and choose actions; practical systems commonly organize that behavior around memory, planning, and action. [1][2]
- Tool-use designs range from prompting a single model to alternate reasoning and calls, through learned API invocation, to modular systems that route tasks among tools or models. [3][4][5][6][7]
- Evaluation must go beyond whether a final answer is correct: tool selection, arguments, execution, planning, robustness, and consistency can fail independently. [8][9]
- Recent work shifts toward long-horizon and realistic evaluation, learning from interaction, trace-grounded oversight, and explicit tool-use safety; the sources also describe approaches that distill tool-produced capabilities toward tool-free inference. [10][11][12][13][14]

## Background
An LLM agent is not simply an LLM that answers a question: in the survey framing, it can perceive an environment and act on it, with the model participating in planning and feedback-driven behavior. A useful architectural decomposition includes role or profile, memory, planning, and action, while another taxonomy groups agent work into tool use, planning (including retrieval-augmented generation), and feedback learning. These taxonomies are complementary: one describes components, the other recurring paradigms. [1][2]

Tool use matters because a model can delegate operations requiring external knowledge, computation, or state changes rather than rely only on parametric knowledge. MRKL exemplifies a modular perspective: a router dispatches requests to neural or symbolic experts, with their outputs returned or passed onward. ReAct instead emphasizes an interaction loop in which reasoning traces inform actions and observations update subsequent reasoning. [3][5]

## From prompted actions to trained and modular tool use
A simple route to agency is to prompt an existing model to alternate reasoning and actions. ReAct interleaves verbal reasoning with calls to external sources, and its reported results show why the combination can matter: on HotpotQA and Fever, ReAct with a Wikipedia API outperformed vanilla action-generation and was competitive with chain-of-thought, while combining the two was reported as best overall. In ALFWorld and WebShop, one- or two-example prompting exceeded imitation or reinforcement-learning methods trained on 10^3–10^5 task instances by 34 and 10 percentage points in success rate, respectively. These results support the value of interaction and prompting in those settings, not a universal advantage across tasks. [5]

A second family teaches the model tool-call behavior. Toolformer generates candidate API calls and retains those that improve prediction of future tokens, then fine-tunes on the retained calls; the studied APIs included calculators, search, translation, Q&A, and calendars. The approach targets when to call, which API to use, arguments, and how to incorporate results. [4][15] Broader tool libraries make selection and orchestration central: ToolLLM couples a dataset, decision tree, automatic evaluation, and neural API retrieval for real-world APIs, while Reverse Chain uses target-driven API selection and argument completion without fine-tuning. [6][16]

Other designs decompose tool use across components. A multi-LLM framework separates planning, invocation, and summarization, with its summary reporting stronger performance than traditional single-LLM approaches. [7] More recent work also explores separating tool selection from argument generation through specialized LoRA adapters, or retrieving stepwise prior experience to support complex multi-step calls. [17][18] Together these approaches trade the simplicity of a single prompted loop for explicit routing, learned specialization, or reusable experience. The available notes report these approaches and their stated results, but do not provide a common controlled comparison across them.

## What benchmarks measure—and miss
Tool-use capability is not a single outcome. Evaluation can separately examine whether an agent decides to invoke a tool, selects the right one, retrieves it, supplies semantically correct parameters, and successfully executes the call. Syntactic checks such as abstract syntax tree correctness may not catch wrong parameter meaning; execution-based assessment helps ground evaluation in what the tool actually did. End-to-end success remains useful, but can hide whether a failure arose in planning, calling, the environment, or recovery. Repeated trials are also relevant because stochastic agents may be inconsistent, though repetition increases evaluation cost. [8]

Benchmarks illustrate different measurement choices. API-Bank provides runnable evaluation with 73 API tools and 314 annotated dialogues containing 753 calls, and separately describes training data across 2,138 APIs and 1,000 domains. Its analysis identifies correct API calls and adherence to API documentation as continuing challenges. [19] For longer-horizon web tasks, Odysseys uses 200 tasks across live websites, derived from annotated browsing behavior, and multiple rubrics per task; its authors argue rubric assessment gives finer signal than trajectory-level binary judging. They report 44.5% perfect task success for the strongest tested model. [10]

Evaluation is also sensitive to environment and task framing. The dual-control τ²-bench setting requires the agent and user to use tools to change a shared environment; reported success fell when agents had to guide users, and the paper notes user-simulator and task-specification errors as sources of benchmark noise. [20] The 2026 Agent Planning Benchmark diagnoses holistic and feedback-conditioned planning, plus robustness to broken, irrelevant, or unavailable tools. Its authors report weaknesses in long-horizon planning, tool-noise robustness, calibrated refusal, and inference-time refinement across 12 MLLMs, underscoring why a final completion score alone is insufficient. [9]

## Reliability, oversight, and learning from interaction
Tool access expands capability but also creates safety obligations: harmful results can arise from direct calls, indirect content, or combinations of steps. ToolSafety contributes a dataset spanning 40 categories and 2,441 tools, including direct-harm, indirect-harm, and multi-step examples; fine-tuning reported improved safety with small helpfulness impact, while cross-language, jailbreak, and worst-of-n risks remained. [14] A separate evaluator, AgentAuditor, uses retrieved memories of past interactions to assess new cases; its ASSEBench covers 15 risk types and 29 scenarios, and the paper reports up to 96.3% F1 on R-Judge for one evaluated model configuration. [21]

For long-running agents, oversight asks not only what they output but why consequential decisions were made. AgentMonBench focuses on requirement–behavior alignment and awareness of consequential autonomous actions, with monitors intended to locate evidence supporting decisions. [11] A related open issue is whether agents genuinely learn from experience rather than merely exploit instructions or prior knowledge. Learn2Play Bench is designed around unfamiliar text-based games to distinguish learning through interaction from reasoning over already-provided rules. [12] These directions make trajectories and evidence—not just final answers—objects of evaluation and governance.

## Trends and open problems
In the last two years covered here, work moves from isolated API-call competence toward multi-step workflows and the conditions needed to trust them. Recent systems emphasize specialization and experience retrieval; evaluation work emphasizes realistic, long-horizon tasks, diagnostic planning tests, and trajectory-level evidence; safety studies specifically target indirect and multi-step harms. [17][18][9][10][11][14]

Another emerging direction is to treat environments and interaction traces as training or evaluation resources. Trace2Env uses historical interaction traces to support stateful simulation when the original system is unavailable, while Learn2Play Bench isolates learning in unfamiliar environments. [22][12] Conversely, SpatialOPSD describes using verified tool-generated traces to distill spatial intelligence toward tool-free inference, motivated by inference overhead and external dependencies associated with tool use. [13] These approaches represent differing aims: making interaction reproducible, measuring adaptation, or internalizing capabilities that otherwise require tools.

Open problems remain. Long-horizon agents need robust recovery from tool errors, calibrated decisions about when not to act, and reliable handling of indirect harm; benchmarks must also avoid conflating agent skill with simulator defects or grading noise. [8][9][10][20][14] Monitoring systems need to provide verifiable evidence across extended action histories, and evaluations need to test whether agents update beliefs appropriately when retrieved evidence conflicts with prior beliefs. A recent proposal operationalizes this latter issue through Identify, Solve, and Escalate trajectory dimensions, highlighting that epistemic humility is distinct from raw tool-call accuracy. [11][23] Across these threads, the central methodological lesson is to evaluate the full interaction process while preserving clear attribution of errors and benefits to the model, tools, and environment. [8][9]
